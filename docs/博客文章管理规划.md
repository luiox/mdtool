# 博客文章管理规划（v1，2026-08-29）

## 1. 背景与痛点

博客源仓库：[luiox/luiox.github.io-src](https://github.com/luiox/luiox.github.io-src)（Hexo，源码与产物分仓）。现状：

- 文章在 `source/_posts/*.md`（当前 26 篇），图片平铺在 `source/assets/`，正文用**相对路径**引用：`![x](assets/xxx.png)`。
- 全流程纯手工：新建文章、front-matter 抄模板、图片手工放进 assets、链接手敲、失效了肉眼排查。hexo-admin（`hexo server -d`）只解决"新建文件"这一步，图片与链接完全不管。
- 图片链接一多就是灾难：文件名对不上、图片进了仓库但链接写错、删了图片链接残留，全靠人工核对。

目标：**把博客源目录当作 mdtool 的一种知识库形态接管**，文章与图片的增、查、校验、发布辅助全部工具化。

## 2. 与现有架构的关系

- **编辑器仍由 Typora 专职**，mdtool 不做编辑（同知识库主流程的分工）。
- **复用现有能力**：图片校验（AST/正则解析）、`libmarkdown` 幂等 AST 读写、文件浏览器、`link_resolver.py` 的目标制改写。
- **链接模型的豁免**：[知识库规范](知识库规范.md) 将"存储改相对路径"否决为**知识库默认**（理由：笔记任意深度时相对路径按深度计算、移动即断链）。博客形态是**有正当理由的例外**：
  - 博客的消费方是 GitHub Pages 静态托管，本地图床 `http://127.0.0.1:8765/...` 对读者不可达，图片必须进仓库、必须相对引用；
  - Hexo 的 `_posts` 是**单层平铺**，不存在"任意深度"问题，相对路径固定为 `assets/<name>`，不会触发规范否决时担心的断链场景。
  - 落地方式：给 `link_resolver.py` 增加 `hexo` 目标（解析 `assets/<basename>` 相对链接），与既有 `zip` 目标并列。**豁免只对博客形态生效，不回渗到知识库默认模型。**

## 3. 分阶段功能

### B0 博客源识别（地基）

- 把含 `_config.yml` + `source/_posts/` 的目录识别为"博客源"，作为文件浏览器的一种数据源（与散装/db 模式并列）。
- 文章列表读 front-matter（标题/日期/categories/tags），按日期排序展示。
- **验收**：打开博客源目录，26 篇文章列表与 front-matter 元数据正确显示。

### B1 新建文章脚手架

- 按 Hexo `scaffolds/post.md` 模板生成新文章，自动填 title/date/filename，替代手工+hexo-admin。
- **验收**：mdtool 新建一篇文章 → `hexo server` 下可见且元数据完整。

### B2 图片闭环（本规划的核心价值）

- **插入图片**：选择/粘贴图片 → 自动按现有命名规则存入 `source/assets/` → 在光标处插入相对链接 `![](assets/<name>)`。
- **校验**：复用图片校验遍历 `_posts` 全量链接，报告：assets 文件不存在、图片无引用（可清）、链接格式异常。
- **迁移**：散落在文章目录的图片一键迁入 `assets/` 并批量改写链接（复用 migrate 能力，目标 `hexo`）。
- **验收**：对现有 26 篇跑一次全量校验，输出的报告与人工核对结果一致；插入一张新图到一篇文章，hexo 渲染可见。

### B3 发布辅助

- 命令面板封装 `hexo clean / generate / server -d / deploy`（subprocess，输出回显）。
- **验收**：mdtool 内完成"写文章 → 插图 → 校验 → 生成预览"全流程，不碰命令行。

## 4. 明确不做

- 不做 Markdown 编辑器（Typora 专职不变）。
- 不接管 Hexo 主题、构建配置、评论系统。
- 不改动知识库默认的图床 URL 模型；`hexo` 相对路径目标是独立分支，不混用。
- 不做多人协作/草稿审阅（个人博客，无此需求）。

## 5. 待定项

- `_drafts/` 是否纳入 B0 列表（倾向纳入，标"草稿"过滤）。
- 图片命名沿用知识库的 `image-YYYYMMDDHHMMSSnnn` 规则还是保留博客原文件名（倾向前者，顺带解决重名）。
