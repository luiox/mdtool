# mdtool 定位与架构分析（v1，2026-08-16）

> 本文是 mdtool 重构的决策依据。结论分两类：**已确认**（用户拍板）与**待定**（需要后续决策）。
> 配套规范文档（链接规范、目录布局规范）在决策落定后从本文拆出。

---

## 1. 产品定位（已确认）

**一句话：个人 Markdown 知识库管理器 + Markdown 工具集。**

| 端 | 角色 | 范围 |
| --- | --- | --- |
| 桌面端（Windows，PySide6） | 知识库**管理器** + 工具集 | 知识库文件夹视图、正则全文搜索、导出（标准 markdown + 图片打包 zip / db 格式，支持单篇与多篇） |
| Typora | 专职**编辑器** | 与桌面端配合，自定义上传器（typora-uploader）保持现状 |
| 手机端（安卓，v1） | 只读**浏览端** | 原生 app + 内置本地 Web 服务器 + WebView 渲染；目录浏览、笔记渲染（含图片）、全文搜索、离线可用 |

**关键决策（已确认）：**

- **散装文件是规范格式，db 容器是受支持的第二存储形态（双模式保留）**：
  - **散装（文件）模式**：知识库 = 一个目录树（笔记 `.md` + 图片 + 附件），是**同步、手机、归档的规范形态**（手机端只支持文件形态）。
  - **db 容器模式（"内存态"）**：正文住 `notes.db`，磁盘只是临时落地场所（RAM 盘 / temp 目录 + watchdog 回写），图片仍是 HTTP URL 由本地媒体服务器渲染、**无需落地**。适用"不能/不想持久落地 markdown"的环境；天然绑定 PC 端（依赖本地媒体服务器），与手机同步解耦。
  - 两种模式**互转保留**（导入文件夹 / 导出为文件夹），db 格式同时是导出格式之一。
- **同步方式**：知识库目录（散装）整体同步到手机（Syncthing / WebDAV / 网盘目录），app 在手机上起本地服务器渲染 → 天然离线。
- **手机端定位 = 纯预览/阅读器**：只支持散装文件形态（同步文件夹），**不支持 db 容器读取**，也不做编辑/上传（桌面端是编写主力，编辑能力不在手机端路线图上）。
- **手机端 v1 不做**：编辑、上传、GC、连接 PC 流式访问。

## 3. 核心架构决策

### 3.1 知识库目录布局（新规范，待细化）

**散装（文件）模式**下，把"媒体根"和"笔记树"合并为**一个 KB 根目录**，一次同步全带走：

```
<kb-root>/                 # 唯一真相源，整体同步到手机
├── notes/                 # 笔记 .md，允许任意子目录
├── images/                # 图片，扁平（沿用 image-YYYYMMDDHHMMSSnnn.* 命名）
├── assets/                # 附件，扁平
└── meta.db                # 媒体元信息（原始名/size/mime，附件回传原始名依赖它）
```

- Typora 打开 `<kb-root>/notes` 编辑；typora-uploader 上传到同一 KB 根的 `images/`（服务器 media_root 指向 KB 根即可，现状兼容）。
- 桌面端"选择项目根目录"即选择 KB 根。
- 存量迁移：现散装笔记目录 + 独立媒体根 → 合并进一个 KB 根，用现有 migrate/导入工具改写链接。

**db 容器（"内存态"）模式**与文件树是并行的第二形态，编辑流程：

```
notes.db（正文真相源）
   │ 导出（单篇/多篇/全库，可只导出相关笔记）
   ▼
落地目录（默认系统 temp；可配置为 RAM 盘路径）
   │ Typora 打开文件夹编辑
   ▼
watchdog 监听改动 → 回写 notes.db（现实现已具备，落地根目录可配置化即支持 RAM 盘）
```

- 图片/附件链接保持 HTTP URL（本地媒体服务器渲染），落地内容只有 `.md` 文本，天然轻量。
- 与散装模式互转：`导入文件夹`（散装 → db）、`导出为文件夹`（db → 散装）；db 格式同时是导出格式。

### 3.2 链接分层模型（核心，决定手机可行性）

**问题**：现状把 `http://127.0.0.1:8765/images/xxx.png` 写死进笔记正文，导致同一份笔记只能在"本机 + 该端口"渲染。手机永远访问不到 PC 的 localhost。

**解法：存储与渲染解耦。** 分层定义：

| 层 | 形式 | 说明 |
| --- | --- | --- |
| 权威标识（canonical） | `/images/image-xxx.png`、`/assets/xxx.pdf`（URL 的 path 部分） | 媒体在 KB 根下的逻辑路径，任何环境可解析 |
| 存储形式 | 完整 URL（现状，host 默认 `127.0.0.1:8765`，可配置） | **零存量迁移**；host 只是"桌面默认渲染基址"，语义上可被替换 |
| 渲染形式 | 按目标环境改写（见矩阵） | 任何消费方不得直接用存储 URL，必须经过 resolver |

**链接解析矩阵（resolver 的职责）**：

| 消费方 | 改写规则 |
| --- | --- |
| Typora（桌面编辑） | 原样（`http://127.0.0.1:8765/...`，本地媒体服务器在跑即可显示） |
| 桌面导出 zip | `http://127.0.0.1:8765/images/xxx.png` → zip 内相对路径（如 `assets/xxx.png` 或按导出结构），附件保留原始文件名信息 |
| 手机端（同步文件） | `http://127.0.0.1:8765/images/xxx.png` → `http://127.0.0.1:<app端口>/images/xxx.png`（前缀替换，app 本地服务器提供媒体） |
| 未来：LAN 直连 / 网页预览 | → `http://<lan-ip>:8765/...` 或自定义基址 |

**实现**：桌面端新建 `link_resolver` 模块（Python，解析 + 改写，所有 tab/导出共用，替换现在散落的正则 ad-hoc 逻辑）；手机端以同一语义在 Kotlin 里实现（逻辑约几十行）。

> 曾考虑"存储相对路径"（`images/xxx.png`，Obsidian 风格）：zip/手机天然可用，但笔记散在任意子目录时相对路径要按深度计算、移动笔记即断链，且需迁移全部存量——**否决为默认方案**，保留为远期可选项。

### 3.3 搜索

| 端 | 方案 |
| --- | --- |
| 桌面 | 正则全文搜索直接扫 `notes/` 下 `.md`（个人规模毫秒级）；`notes.db` 若保留为索引缓存则仅作加速 |
| 手机 | v1：遍历 + 子串/正则匹配（KB 规模下够快，实现最简）；若慢，升级 SQLite FTS5 trigram（对中文子串友好） |

### 3.4 手机端架构（原生 app + 内置本地服务器）

用户的构想（app 内起本地 Web 服务器 + WebView 渲染）成立，组件拆解：

```
安卓 app（Kotlin + Compose，推荐）
├── 知识库目录访问        # 读取同步到手机的 KB 根（app 私有目录或用户可访问目录）
├── 嵌入式 HTTP 服务器    # ktor 或 NanoHTTPD，绑定 127.0.0.1:<端口>
│   ├── /images/* /assets/*  静态媒体（附件按 meta.db 回传原始文件名）
│   ├── /note/*          笔记服务端渲染：md → HTML（flexmark）+ 链接 resolver 改写
│   └── /search          搜索接口（或端上直接扫）
├── WebView              展示渲染后的 HTML（可后接 KaTeX/Mermaid 增强）
└── 搜索模块              建索引 / 遍历匹配
```

- **技术栈痛苦的正确解法**：不把 Python 服务器搬上安卓（Chaquopy 付费 / Termux 体验差）。手机端服务器组件很小（静态服务 + md 渲染 + 链接改写，约数百行），用 JVM 生态重写成本可控；**跨端共享的是规范（3.1/3.2），不是代码**。
- 服务端渲染（flexmark）与桌面导出 zip 共用同一"渲染/改写语义"，避免两端渲染结果不一致。
- 备选：Flutter（跨端收益目前用不上，暂列备选）。

### 3.5 桌面端 UI 收敛

按"知识库管理器 + 工具集"定位重组，两个层级：

- **知识库主流程**（首屏）：文件夹视图（KB 根）+ 正则搜索 + 导出（zip / db，单篇 / 多篇）+ 打开 Typora；**双模式并存**——散装文件树浏览 + db 容器（导入/导出/内存态编辑）。
- **维护工具**（次级）：本地媒体服务器（含 GC）、图片校验、图片迁移、空格修复。工具栏/次级 tab 承载，不再与主流程平级堆砌。

## 5. 待定项（需后续决策）

1. **同步工具选型**：Syncthing（双向、无云依赖、安卓端成熟）/ 坚果云 WebDAV（国内网络友好）/ OneDrive 等网盘目录。决定手机 app 的目录访问方式与冲突策略。
2. **安卓技术栈定稿**：Kotlin + Compose（推荐，flexmark/NanoHTTPD 生态成熟）vs Flutter。
3. **手机端搜索策略**：先遍历+正则，还是直接上 FTS5 trigram。
4. **meta.db 是否随 KB 根同步**：附件回传原始文件名依赖它；不同步则手机端附件按时间戳名下载（可接受降级）。
5. **存量数据迁移方案细节**：现有笔记目录与媒体根如何合并为 KB 根，链接如何批量改写（复用 migrate tab 能力）。
6. **桌面搜索是否保留 notes.db 索引缓存**：还是纯扫文件（更简单）。

## 6. 需求与约束清单（链接规范决策依据）

| 约束 | 内容 | 对设计的影响 |
| --- | --- | --- |
| C1 | Typora 是唯一编辑入口，必须能渲染插入的图片 | 存储形式必须 Typora 可解析：完整 URL 或本地路径（相对路径受 C3 限制） |
| C2 | 存量笔记全部是 `http://127.0.0.1:8765/...` 完整 URL | 存储规范应兼容现状，避免全量迁移 |
| C3 | 文件即真相后笔记会移动/重命名 | 否决"存储相对路径"默认方案（移动即断链） |
| C4 | 媒体扁平存放（images/assets），与笔记位置无关 | 权威标识 = URL path，与笔记位置解耦 |
| C5 | 手机端 = 同步文件夹 + 本地服务器 | 链接改写 = 前缀替换，resolver 语义在两端一致 |
| C6 | zip 导出需要 zip 内相对链接 | 导出时由 resolver 改写（导出器不依赖存储形式） |
| C7 | 附件下载需回传原始文件名 | 依赖 meta.db（或导出时把原始名写进链接/旁路清单） |
| C8 | 手机端要全文搜索且离线 | 搜索基于本地文件，与渲染共用 KB 根 |
