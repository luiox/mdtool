# 仓库形式与合并包规范

> 状态：**设计定稿，待实现**（2026-09 讨论）。本文记录稀疏导出/合并导入、仓库形式统一约定与备份方案的决策。
> 标注 ✅ 的为已拍板结论，⬜ 为实现期事项。落地后 §1 目录布局回填 `docs/知识库规范.md`（一处事实一个家）。

## 0. 要解决的问题

1. **稀疏导出**：选中一篇/几篇笔记（或一个文件夹 + 额外几篇）导出为可搬运的包（zip 或 db）。
2. **合并导入**：把包导入现有库时，同一路径的笔记先看 diff 再逐条决定，绝不静默覆盖
   （现状 `_import_folder_job` 同路径直接 upsert，是数据安全隐患，本功能落地后退役）。
3. **备份**：KB 根单文件夹交给去重备份工具（选定 Kopia），月度快照，媒体不重复占空间。

---

## 1. 仓库形式（统一目录约定）✅

一切形态都是同一套目录约定的完整度差异：**工作库 = 完整仓库形式；bundle = 其子集 + manifest。**

| 条目 | 工作库（散装） | bundle.zip | bundle.db |
| --- | --- | --- | --- |
| `kb.json`（服务器配置） | ✅ | ✅ | ✅（存 `bundle_meta` 表） |
| `manifest.json`（清单+hash） | ❌ 不需要 | ✅ | ✅（存 `bundle_meta` 表） |
| `markdown/**.md`（笔记树） | ✅ 全量 | ✅ 子集 | ✅ 子集 |
| `images/*`、`assets/*`（扁平媒体） | ✅ | ✅ 被引用的 | ✅ 被引用的 |
| `meta.db`（媒体元信息） | ✅ | ✅ **子集**（仅随包媒体的行） | ✅（即大 db 内的同名表） |
| `notes.db`（仅 db 模式工作库） | ✅ 默认放 KB 根 | — | — |

### 1.1 各条目职责

- **`kb.json`**：服务器与布局配置。字段 = 现有 `DEFAULT_CONFIG` 减 `media_root`
  （仓库形式下根即媒体根，该字段消失）：`host` / `port` / `images_subdir` / `assets_subdir` / `format_version`。
  存量库没有此文件按默认值兜底（127.0.0.1:8765，images/assets）；首次导出时顺手补写。
- **`markdown/`**：笔记目录，**由 `notes/` 改名而来**（✅ 用户拍板）。迁移方式：
  - 桌面代码做**双名兼容**：读取向优先识别 `markdown/`，不存在则退 `notes/`；
  - 存量库手动改文件夹名，不做迁移工具；Typora 重新打开新目录；
  - 安卓端 `KbRepository.kt` 一处硬编码改为"先找 `markdown/` 再退 `notes/`"；
  - 笔记内链接不受影响（存的是绝对媒体 URL；笔记间相对互链只要不经过被改名的根段就不断）。
- **`images/`、`assets/`**：扁平时间戳名文件，**只增不改**（上传即落盘定名，从不改写旧文件；
  GC 是唯一减法）。这是备份去重和增量对账的前提纪律。
- **`meta.db`**：媒体元信息（`timestamp_name → original_name/size/mime/upload_time`）。
  **定位修正：这是知识库数据而非本机缓存**——附件原始名不可再生，必须随库走、随包走。
- **`notes.db`**（db 模式）：正文真相源。默认放在 KB 根内，使 db 工作库同样收缩为单文件夹
  （备份工具单源覆盖）。RAM 盘落地目录只是临时投影，不属于仓库形式、不入备份。

### 1.2 身份模型 ✅

- **笔记身份** = `markdown/` 下相对路径（posix、无前导斜杠，同 `NotesDB.normalize_path`）。
- **媒体身份** = URL path（`images/image-xxx.png`），即知识库规范 §2 的权威标识，跨机器天然可比。
- 因此"同一个东西"的判定就是路径相等，无模糊匹配。Windows 下路径比较一律 casefold。

## 2. 合并包格式 ✅（`mdtool/core/kb_bundle.py`）

### 2.1 链接存储原则 ✅

**包内笔记保存原始存储形式（绝对 `http://host:port/...`），不做预改写。**
来源 host/port 记录在包内 `kb.json`；导入时按目标配置做前缀替换——与手机端 resolver 同语义。
理由：分享 zip 的相对链接改写是有损的（旧版相对路径图片归入 `assets/` 无法逆向），合并导入需要保真。
现有"分享 zip"导出保持不变，两种包各司其职。

### 2.2 manifest.json schema ✅

纯清单职责：管互换对账，不管业务元数据（原始文件名由 meta.db 管）。

```json
{
  "format": "mdtool-bundle",
  "version": 1,
  "created": "2026-09-01T00:00:00Z",
  "items": [
    {"path": "markdown/a/b.md",     "kind": "note",  "sha256": "...", "size": 123},
    {"path": "images/image-x.png",  "kind": "image", "sha256": "...", "size": 45678},
    {"path": "assets/y.pdf",        "kind": "asset", "sha256": "...", "size": 89}
  ]
}
```

- sha256 按**原始字节**计算；mtime 可选字段（UI 展示用）。
- 只登记**实际随包**的文件；未随包的引用不入 manifest（见 §3.2 三方对账）。
- 来源信息不重复存，读包内 `kb.json`。

### 2.3 bundle.zip ✅

zip 根即仓库形式根（`manifest.json` 在 zip 根，无包裹层目录）：
`manifest.json` + `kb.json` + `markdown/**` + `images/*` + `assets/*` + 子集 `meta.db`。

### 2.4 bundle.db ✅

单文件序列化，schema：

```sql
notes       -- 与工作库 schema 完全一致（NotesDB 原样复用）
media       -- path TEXT PRIMARY KEY, sha256 TEXT, size INTEGER, data BLOB
            -- path 用 'images/x.png' 形式，与 zip 内路径同约定
images      -- MetaDB 原表结构
assets      -- MetaDB 原表结构
bundle_meta -- key TEXT PRIMARY KEY, value TEXT；存 manifest JSON 与 kb.json 内容
```

- **判别标志**：打开 .db 时查 `bundle_meta` 表是否存在——有 = 合并包，无 = 普通工作库。
- 导出 = items 写三张表；导入 = 读出为同样的 items 列表。

### 2.5 媒体可选导出 ✅

大附件不强制随包。导出对话框先扫描引用给出统计，再让用户决定：

```
选中 12 篇笔记
├─ 图片 45 个，共 38 MB        [✓] 包含图片
└─ 附件 6 个，共 412 MB        [✓] 包含附件   单文件超过 [20] MB 则跳过
```

- 图片/附件分开开关 + 单文件大小阈值（阈值 0 = 不过滤）。默认值（图片必带、附件可关、20MB）
  实现时可调。P3 再考虑逐文件勾选排除。
- **不带文件 ≠ 链接必断**：目标库可能同名已有该媒体（见 §3.2）。
- meta.db 子集只跟随包集合走（避免出现有记录没文件的行，与 GC 打架）。

## 3. 导入合并语义 ✅（纯函数 `kb_bundle.classify_import/apply_import`，UI `qtui/tabs/bundle_io.py`）

### 3.1 管线分层（纯函数，参考 plan_zip_bundle 模式，新模块 kb_bundle.py）

```
read_bundle(zip/db/folder) -> items[(path, kind, bytes, sha256)]
classify(items, target)    -> [{item, status: 新增|相同|冲突|媒体状态…}]   # 纯函数，可单测
apply(plan, 用户逐条决定)   -> worker job（qtui/workers.py + logbus）
```

三个薄适配器（文件夹 / zip / db）共用同一分类器与 diff UI；文件夹来源即升级版合并导入，
替代 `_import_folder_job`。

### 3.2 媒体三方对账 ✅

导入端把每篇笔记过 resolver 改写 host:port 时顺手收集全部媒体引用，逐一判定：

| 引用的媒体 | 状态 | 处理 |
| --- | --- | --- |
| 在包里 | 随包 | 落地到目标 media_root 对应子目录 |
| 不在包里，目标库同名已存在 | 目标已有 | 什么都不做，链接本来就好使 |
| 两边都没有 | 缺失 | 日志警告"`a.md` 引用的 assets/x.pdf 未随包且本库没有" |

由此获得的能力：可以反复发"只含文字改动"的小包，媒体一次到位即可。

### 3.3 冲突处理 ✅

- 文本比较前做 **CRLF/BOM 归一化**，归一化后相同 = 无冲突（避免 Windows 编辑器制造假冲突）；
  但落地写入保留包内字节原样。
- 冲突条目**逐条看 diff 由用户决定**（双栏只读 QPlainTextEdit + difflib 高亮，v1 可先统一 diff 着色）；
  **未明确点过的条目一律按跳过落地**（安全兜底）；不做"全部覆盖"批量按钮。
- 媒体同名不同内容：概率趋零（时间戳名），以包内为准 `INSERT OR REPLACE`，日志告警即可。
- meta.db 行合并：`INSERT OR REPLACE`（正是 `MetaDB.add_image/add_asset` 现成语义）。
- URL 改写：来源 `kb.json` 的 host:port → 目标当前配置，前缀替换。

### 3.4 安全项 ✅

- zip slip 防护：拒绝绝对路径与包含 `..` 的成员名。
- sha256 校验失败 → 拒绝该条目并报告，不带病落地。
- `format` 不是 `mdtool-bundle` 或 `version` 高于本机支持 → 拒绝导入并提示升级。

## 4. db 模式调整 ✅（`kb_bundle.migrate_meta_into_db` + library 页打开库时自动迁移 + `MediaServerTab.set_meta_override`）

1. **媒体元数据并入大 db**：`MetaDB` 的建表全是 `CREATE TABLE IF NOT EXISTS`，
   连接直接指向 notes.db 即与 notes 表共存。散装模式照旧用 `meta.db` 文件，
   db 模式激活期间媒体服务器指向 notes.db。
2. **存量自动一次性迁移**：打开 db 库时，若 media 根存在旧 `meta.db` 且大 db 内 media 表为空
   → `ATTACH + INSERT OR REPLACE SELECT` 搬入，旧文件改名留底（如 `meta.db.migrated`）。
3. **边界不动**：进大 db 的只是元数据表；**媒体字节仍是文件**，继续走图床 URL 渲染
   （db 容器正文轻量的架构决策不变）。
4. **notes.db 默认放 KB 根**（§1.1）。

## 5. 备份方案（Kopia）✅ 选型 / ⬜ 配置

### 5.1 原理

KB 根是**单一文件夹**，直接作为 Kopia 快照源。月度跑一次：

- 第一次全量入库；之后 `images/` `assets/` 内容从不变，在 Kopia 去重账本上全部命中、零新增存储；
- 每个快照是独立时间点，**可随时恢复到任意历史状态**（`kopia restore` 到目录或 `kopia mount` 只读浏览）。

前提纪律：§1.1 的"媒体只增不改"。GC 删除后跑一次快照即对齐；被删文件仍可从历史快照恢复。

### 5.2 推荐配置（安装后对照 `kopia --help` 核实具体 flag）

| 项 | 建议 |
| --- | --- |
| 源 | KB 根（唯一源；RAM 盘落地目录**绝不**入源） |
| 压缩 | **zstd**——注意 Kopia 默认不压缩，必须在 policy 显式开启 |
| 调度 | Windows 任务计划程序月度触发 `kopia snapshot create <kb-root>`（Kopia 自带调度是间隔制，非日历制） |
| 保留策略 | keep-monthly ≥ 12（配合少量 keep-latest），按硬盘预算调 |
| db 模式附加步骤 | 快照前先做 sqlite 一致性拷贝（python `sqlite3` 备份 API 或 `.backup`），
    避免快照到写入中的库；散装模式无需此步（真相就是文件树） |
| 恢复演练 | 定期 restore 到临时目录并只读打开验证，不直接盖工作库 |

> 注：以上 Kopia 细节基于既有知识编写，本会话无法联网核实；装好后逐项对照官方文档确认再固化成脚本。

### 5.3 与其他方案的关系

- 硬链接合成全量 / 按名增量脚本（备选方案 2/3）不需要工具配合，留作 Kopia 不可用时的退路。
- **备份不用 bundle 格式**：bundle 是搬运/合并语义（无删除、无全量恢复概念），备份留在文件系统层。
- 方向反哺：manifest 的 sha256 积木将来可做 P3"只导出某日期以来的改动"。

## 6. 边界与已知限制

| 项 | 说明 |
| --- | --- |
| 笔记互链不改写 | 包内 `.md` 相对互链原样透传（身份=路径，整树结构保留）；部分导出时目标不在包里则同 §3.2 对账逻辑对待 |
| 手机同步 | `notes/`→`markdown/` 改名后 Syncthing 侧路径变化需重新确认共享；安卓双名兼容过渡 |
| typora-uploader | 上传目标 media_root 不变，无影响 |
| 大小写 | Windows 路径比较 casefold；db 模式经 rename 可能产生仅大小写不同的两行，分类器按 casefold 视为同路径冲突 |

## 7. 明确不做

- 删除同步语义（包不含删除指令）。
- 自动三方文本合并 / hunk 级选择（v1 整篇二选一，diff 自审）。
- 手机端任何改动（只读端不受影响）。
- 把备份做成 bundle 格式。
